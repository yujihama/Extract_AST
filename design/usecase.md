### ユースケース洗い出しの軸

> このファイルは **「今回の一連の改修（N-doc対応 / pre_analysis主導の実行計画 / テンプレ入力 / is_complete時の成果物保証 / ルールベース分岐削除）」** を踏まえて、
> 各ユースケースが **現時点で実現可能か** を評価し、想定される挙動（入力→処理→成果物）と制約を記載する。

- **入力形態（ドキュメントの組み合わせ）**
  - **単一文書**（1 doc）
  - **2文書**（比較/参照/移植：A vs B）
  - **基準 + 1文書**（規格/法令/社内基準 → 対象文書を評価）
  - **基準 + 複数文書**（基準 → N文書を横断評価、部門別/製品別など）
  - **複数文書の合成**（N docs → 1成果物）
  - **版管理（時系列）**（v1→v2→v3、改訂履歴・影響分析）
  - **コーパス（大量文書）**（検索・分類・ナレッジ化、RAG前提）
  - **マルチモーダル**（PDF図表/画像/スキャン、表や注記が重要）

- **目的/出力形態（何を作るか）**
  - **評価**（準拠/網羅/リスク/品質をスコア・根拠付きで）
  - **差分/ギャップ**（抜け・矛盾・変更点・影響）
  - **抽出/構造化**（表・項目・義務・条件をスキーマへ）
  - **生成/ドラフト**（開示資料、回答書、要約、手順書、テンプレ記入）
  - **検索/問合せ**（根拠提示付きQ&A、トレーサビリティ）
  - **整合/統合**（用語統一、重複排除、参照関係の再構成）

### 入力形態（ドキュメント組み合わせ）の対応状況（今回改修の効果）

- **前提（現行実装に基づく）**
  - `mode=real` の主要ステップ（`build_blueprint_all` / `pre_analysis` / `execute_analysis`、および比較準備のEmbedding）は **LLM API key が必須**（`OPENAI_API_KEY` または `AZURE_OPENAI_API_KEY`）。
  - `request_text` は **`pre_analysis` / `execute_analysis` の必須入力**（Run作成時に `config.json` と `params` に保存され、ステップが参照）。
  - 最終成果物は原則 `data/runs/{run_id}/out/template_filled.md`（artifact kind: `template_filled`）。
  - `pre_analysis` が `is_complete=true` と判断した場合、`pre_analysis` の時点で `out/template_filled.md` を生成し、`execute_analysis` は **存在チェックのみ**で完了する（成果物保証）。
  - N-doc の「比較準備」は `compare_setup` ステップではなく、`execute_analysis` 内のツール `pair_compare_setup(doc_a_id, doc_b_id, purpose)` を **ペアごとに**実行して行う（出力は `work/pairs/<a>_<b>/...`）。
  - `compare_*` 系ツール（差分/グルーピング/チャンク取得など）は **doc_a_id/doc_b_id を必須**とし、ペアごとに状態を復元して動作する。
  - 本文検索は **単一ドキュメントのAST** を対象に `search_by_keyphrase(file_path, phrase, intent)` で行う（ペア非依存）。

- **単一文書（1 doc）**: **可能**
  - 想定挙動: `ensure_text_all → build_blueprint_all → build_ast_all → (summarize_ast_all任意) → pre_analysis → execute_analysis`。タスクが軽量なら `pre_analysis.is_complete=true` により `pre_analysis` で `template_filled.md` まで生成されうる。
  - 制約: `execute_analysis` は必ずしも「比較」ではなく、文書参照ベースの実行（要約/抽出/整形等）として動作する。要求が曖昧だと出力品質がブレるため `request_text` の具体性に依存。
- **2文書（A vs B）**: **可能**
  - 想定挙動: N-doc の特殊ケース（N=2）として扱う。必要なペア準備（Embedding/初期マッチング）は `pair_compare_setup` で実施し、差分や影響を `template_filled.md` に反映。
- 補足: `compare_setup` ステップは廃止し、比較準備は `pair_compare_setup` に統一する。
- **基準 + 1文書**: **可能（役割推定・章立てはLLM主導）**
  - 想定挙動: `pre_analysis` が「基準/対象」の役割を推定し、根拠抽出と評価の章立てテンプレを生成。`execute_analysis` が計画に沿って参照・記入する。
- **基準 + 複数文書**: **可能（小〜中規模のNで現実的）**
  - 想定挙動: `pre_analysis` が評価設計（観点・対象範囲・必要ペア）を立て、`execute_analysis` が必要ペアのみ `pair_compare_setup` で準備して横断レポートを生成。
  - 制約: ペア数が増えると \(O(N^2)\) でコスト/時間が増える。計画（`execution_plan`）次第で実行量が大きく変動する。
- **複数文書の合成（N docs → 1成果物）**: **可能**
  - 想定挙動: `pre_analysis` が統合方針とテンプレを生成し、`execute_analysis` が複数文書を参照して単一成果物に統合する。
- **版管理（v1→v2→v3…）**: **部分的に可能**
  - 想定挙動: v1/v2/v3 を「複数文書」として扱い、`pre_analysis` が比較すべきペア（例: v1→v2, v2→v3）を選び、改訂点と影響を章立てして出力。
  - 制約: line-by-line の厳密赤入れ、改訂履歴の厳密追跡、差分の完全網羅は未保証（LLM判断に依存）。専用の版管理データモデル/差分UIは未実装。
- **コーパス（大量文書）**: **未対応（RAG/高速検索は現状スコープ外）**
  - 現状できること: ドキュメント自体は `data/documents/{doc_hash}/...` に永続化され、Runを跨いで再利用できる（ドキュメント一覧UI/APIあり）。
  - 未対応の理由: 大量コーパス向けの永続インデックス、BM25/ベクタDB等の高速検索、関連文書推薦といったRAG基盤は未実装。N-doc 実行は可能でも「大量」を前提とした運用設計には耐えない。
- **マルチモーダル（図表/画像/スキャン）**: **部分的に可能**
  - 想定挙動: PDF入力は `ensure_text_all` で `fast|llm` のPDF→TXT変換によりテキスト化。さらに必要に応じて、PDFページを画像化して読む `analyze_visual_contents` を比較/blueprint生成のツールとして使用可能。
  - 制約: OCRや表抽出の堅牢化、画像中心PDFの安定処理は未整備。PDFのページ指定や `use_image` の設定によりコスト/時間が大きく変動する。

### 主要ユースケース

#### 1) 準拠評価（Compliance / Conformance）
- **法令・規格・社内基準に対する規程/手順の評価**（基準 + 規程 → 適合/不適合/要改善、根拠箇所、改善案）
- **チェックリスト自動生成と証跡紐付け**（基準 → チェック項目一覧 + 各項目の根拠リンク）
- **監査向けレポート**（複数文書 → 監査用サマリ、例外一覧、是正計画ドラフト）

- **評価（可否）**: **可能（ただし“監査品質”はプロンプト/テンプレ設計に依存）**
- **想定挙動**
  - `pre_analysis`: 基準/対象/補助文書の役割を推定し、評価観点と章立てテンプレを作成。必要なら対象ペアの比較準備を実行。
  - `execute_analysis`: 実行計画（`execution_plan`）に沿って根拠（該当箇所）を参照しながら適合/不適合/要改善を記入し、`out/template_filled.md` を生成。
- **制約**
  - 厳密な条文番号マッピングや“完全網羅”は保証しない（LLMの判断に依存）。
  - クリックで原文定位できるような「機械可読トレースID体系」は未整備（レポート内の引用/根拠記述が中心）。

#### 2) ギャップ分析（Gap / Missing / Coverage）
- **要求事項の抜け漏れ検出**（要求仕様 + 設計/手順 → 未対応要求、対応箇所、追加対応案）
- **RFP/RFIへの回答支援**（RFP + 自社資料群 → 質問ごとの回答ドラフト、根拠、未充足の明確化）
- **セキュリティ/プライバシーのギャップ**（基準 + 運用/規程/契約 → リスクと不足条項）

- **評価（可否）**: **可能**
- **想定挙動**
  - `pre_analysis`: “要求（基準）→証拠（対象文書）” の対応付け方針（チェックリスト/表形式など）を決め、必要ペアの比較準備を実行。
  - `execute_analysis`: 未対応/部分対応/対応済みを分類し、根拠箇所と追加案を `template_filled.md` に反映。

#### 3) 差分・改訂影響分析（Redline / Change Impact）
- **版間比較と影響**（v1 + v2 → 変更点の分類、影響範囲、要更新ドキュメント候補）
- **契約改訂の影響**（旧契約 + 新契約 + 運用手順 → 変更に伴う作業/リスク）
- **法改正対応**（旧法令 + 新法令 + 社内規程群 → 必要改訂箇所の抽出と優先度）

- **評価（可否）**: **可能（all-pairsも可能、ただし計算量増）**
- **想定挙動**
  - `pre_analysis`: 比較対象ペア（例: 旧→新、旧契約→新契約、法令→規程群）を決め、ペアごとに比較準備を行う計画を作る。
  - `execute_analysis`: ペアごとの差分候補（embedding類似＋必要ならLLM）を使い、変更点分類と影響（タスク/リスク）を出力。
- **制約**
  - “赤入れ（line-by-line）” のような厳密差分は専用UI/差分エンジン未実装のため、現状はレポート形式が中心。
  - 差分抽出は `execution_plan` とツール呼び出し設計に依存し、完全性は保証しない。

#### 4) トレーサビリティ（Traceability / Mapping）
- **条文→社内規程→手順→証跡の紐付け**（基準 + 規程群 + 手順/記録 → マッピング表、未紐付け一覧）
- **要件→設計→テスト**（要求 + 設計 + テスト仕様 → トレースマトリクス、欠落/矛盾）

- **評価（可否）**: **部分的に可能**
- **想定挙動**
  - `pre_analysis`: トレース表のテンプレ（行=要求/条文、列=規程/手順/証跡 等）を作り、比較すべきペアや参照優先順を決める。
  - `execute_analysis`: ペア比較ツールを使って対応候補を列挙し、未紐付け/矛盾を記載。
- **制約**
  - トレースの“機械可読な一貫ID体系”や“完全な参照リンク（UIでクリックして原文定位）”は未整備。
  - 監査レベルの再現性（同一入力→同一出力の保証）は未提供（LLMの非決定性が残る）。

#### 5) 生成・ドラフト作成（Synthesis / Drafting）
- **開示資料ドラフト**（基準 + 複数インプット → 章立て案 + ドラフト + 出典注記）
- **規程/手順書の初稿**（複数文書 + 目的/制約 → ひな形 + 初稿）
- **顧客向け回答書**（問い合わせ + 契約/仕様/FAQ → 回答草案、根拠、注意事項）

- **評価（可否）**: **可能**
- **想定挙動**
  - `pre_analysis`: テンプレが与えられればそれを種にし、無ければ生成。章立てと作成方針（出典の扱い、前提/免責、トーン等）を実行計画に落とす。
  - `execute_analysis`: 複数文書を参照してドラフトを埋め、`out/template_filled.md` を生成（簡易タスクなら `pre_analysis` の `is_complete=true` で完結するケースもある）。

#### 6) 抽出・構造化（Extraction / Normalization）
- **義務/禁止/期限/条件の抽出**（法令/契約 → obligations JSON、期限、罰則、例外条件）
- **表・定義・用語集の抽出**（PDF含む → 定義集、参照関係、用語統一候補）
- **フォーム/申請要件抽出**（手続文書 → 必須添付、手順、提出先、期限）

- **評価（可否）**: **可能（ただし“厳密JSON出力”はテンプレ/プロンプト次第）**
- **想定挙動**
  - `pre_analysis`: 抽出したい項目のスキーマ（Markdown表 or JSONブロック）をテンプレ化し、抽出ルール（優先順位/例外）を計画化。
  - `execute_analysis`: 文書から該当箇所を参照して抽出結果を埋める。
- **制約**
  - 表抽出やPDFのレイアウト依存が強い場合、安定性は入力品質に左右される。
  - 厳密なJSONスキーマ拘束はテンプレ/プロンプト設計に依存（スキーマ違反の自動リトライ・検証パイプは未整備）。

#### 7) 品質点検（Quality / Consistency）
- **文書内の矛盾・参照切れ・定義不一致**（単一〜複数 → 指摘一覧 + 修正案）
- **テンプレ準拠チェック**（テンプレ + 対象文書 → 不足セクション、形式逸脱）
- **数値/固有名詞の整合**（複数 → 不一致検出、優先ソース提案）

- **評価（可否）**: **可能**
- **想定挙動**
  - `pre_analysis`: 点検観点（定義、参照、数値、用語）と報告フォーマットをテンプレ化。必要に応じて比較準備（ペア）を実行。
  - `execute_analysis`: 不一致/参照切れ候補を列挙し、修正案や“優先ソース”を提案。

#### 8) 要約・ブリーフィング（Summarization）
- **役割別要約**（単一 → 経営向け/現場向け/監査向けの要点、意思決定事項）
- **差分要約**（v1+v2 → 変更サマリ、対応タスクの提案）

- **評価（可否）**: **可能**
- **想定挙動**
  - `pre_analysis`: 役割別の章立て・粒度・強調点をテンプレ化（テンプレ入力にも対応）。
  - `execute_analysis`: 文書（または差分ペア）を参照しつつ要点を埋める。簡易なら `pre_analysis` 完結（`is_complete=true`）もあり得る。

#### 9) 検索・Q&A（RAG / Evidence-backed QA）
- **根拠付き質問応答**（コーパス → 回答 + 引用 + 信頼度/未確定の明示）
- **社内ナレッジ化**（大量文書 → インデックス、タグ、関連文書推薦）

- **評価（可否）**: **部分的に可能（小規模Nに限定）**
- **想定挙動**
  - `pre_analysis`: 質問リストや回答テンプレ（Q/A/根拠/未確定）を作る。必要なら代表ペアで比較準備。
  - `execute_analysis`: 与えられた文書群の範囲で検索・引用し、回答を作成。
- **制約**
  - RAGの前提となる「大量コーパスの永続インデックス」「高速検索」「関連文書推薦エンジン」は未実装。
  - “検索”はRunに与えた文書群の範囲に閉じる（ドキュメントリポジトリ全体の横断検索は未提供）。

#### 10) 多言語・表現変換（Translation / Rewriting）
- **翻訳（法務/技術含む）**（単一 → 対訳 + 用語統一 + 注意喚起）
- **社内向けに平易化**（難解文書 → 平易版、元文との対応）

- **評価（可否）**: **可能**
- **想定挙動**
  - `pre_analysis`: 出力言語・文体・用語統一方針をテンプレ化（対訳形式も可）。
  - `execute_analysis`: 文書を参照しつつ変換結果を生成し、必要に応じて原文対応（対応表/注記）も出力。

### 拡張ユースケース

#### 11) 提案評価・ベンダー比較（Proposal Evaluation）
- **RFPへの提案書評価**（RFP + 提案書A + 提案書B → 要件適合度、比較表、推奨と根拠）
- **製品・サービスの比較**（評価基準 + 製品仕様A + 製品仕様B → 比較マトリクス、優劣分析）
- **入札審査支援**（入札仕様 + 入札書類群 → スコアリング、審査レポート）

- **評価（可否）**: **可能**
- **想定挙動**
  - `pre_analysis`: 評価基準（RFP要件や評価シート）を解析し、評価観点と比較テンプレを生成。必要な提案書間のペア比較準備を計画。
  - `execute_analysis`: 各提案書を評価基準と照合し、適合/不適合/部分適合を判定。比較表を作成し、推奨候補と根拠を記載。
- **制約**
  - 定量評価（価格、数値仕様）は精度が入力の記載形式に依存。
  - 主観的評価（提案の説得力、実現性）はLLM判断となり、人間レビューが必須。
- **応用ドメイン**
  - システム導入ベンダー選定
  - 業務委託先・外注先の選定
  - M&Aにおける複数候補の比較

#### 12) M&A デューデリジェンス統合（Due Diligence Integration）
- **DD報告書の統合分析**（法務DD + 財務DD + 事業DD → リスク統合、優先度付け、交渉論点）
- **チェックリストとの突合**（DDチェックリスト + 調査報告書 → 未確認項目、追加調査要否）
- **表明保証条項の検討支援**（DD発見事項 + 契約書ドラフト → 反映すべき条項、補償範囲）

- **評価（可否）**: **可能**
- **想定挙動**
  - `pre_analysis`: DD報告書の種類と構造を把握し、リスク項目の統合テンプレを生成。チェックリストとの突合計画を作成。
  - `execute_analysis`: 各DD報告書からリスク項目を抽出し、重複排除・優先度付けを行う。契約反映事項やクロージング条件をまとめる。
- **制約**
  - 専門的判断（法的リスクの重大性、財務影響の見積り）は専門家レビューが必須。
  - 機密性の高い情報を扱うため、運用上のアクセス制御が重要。
- **応用ドメイン**
  - M&A/投資案件のリスク評価
  - PMI（Post Merger Integration）課題の特定
  - JV/アライアンス検討

### ドメイン別応用例

各ユースケースは、以下のドメインで横展開可能。テストデータは `data/input/USECASE_GUIDE.md` を参照。

#### 医療・ヘルスケア
- **準拠評価**: 医療情報システム安全管理ガイドライン vs 病院IT規程
- **差分分析**: 治験プロトコルの版比較（v1→v2）、IRB再審査要否の判定
- **抽出**: 同意説明文書からの義務・リスク・費用条項の構造化

#### 金融・銀行
- **準拠評価**: AMLガイドライン vs 銀行AML規程
- **トレーサビリティ**: 与信審査システムの要件→設計→テストの対応確認
- **ギャップ分析**: 金融規制要件への対応状況

#### 人事・労務
- **ギャップ分析**: 労働法要件 vs 就業規則
- **差分分析**: 就業規則改定の影響（v1→v2）、届出・周知要否の判定
- **抽出**: 人事評価制度ガイドラインからの評価基準・プロセスの構造化

#### 製造・品質管理
- **準拠評価**: ISO 9001要求事項 vs 品質マニュアル
- **品質点検**: 製品仕様書と検査手順書の整合性確認
- **トレーサビリティ**: 製品要求→設計→検査の対応マッピング

#### 入札・調達
- **提案評価**: RFP要件 vs 複数ベンダー提案書の比較・スコアリング
- **ギャップ分析**: RFP要件への各提案の適合度分析
- **ドラフト作成**: 評価報告書・選定理由書のドラフト

#### M&A・投資
- **DD統合**: 法務DD + 財務DD報告書の統合リスク分析
- **抽出**: DD報告書からのリスク項目・推奨対応の構造化
- **差分分析**: 契約ドラフトの版比較、交渉経緯の追跡
